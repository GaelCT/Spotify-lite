## RESOLUTION — next session (2026-11-12)

The OPEN ISSUE above is **diagnosed and handled; the verdict is that playback cannot be fixed client-side for this account.**

### Root cause (confirmed with live evidence)

The playback failure is **not** the login5 lock (that fix works — the session authenticates). It is Spotify's **server-side, per-account denial of audio keys** for accounts created after an apparent ~2024/2025 cutoff:

- App log signature: `Authenticated as '3l982qduoe8rc2lqe14jkytxf'` → metadata loads → `ERROR librespot_core::audio_key: error audio key 0 1` → `Service unavailable { audio key error }` → Symphonia chokes on the still-encrypted file → skip. Every track, every attempt.
- "0 1" = the AP's 2-byte big-endian error code **0x0001** (`AesKeyError`) — hard, permanent refusal.
- **Live probe** (`examples/playback_probe.rs`, fresh keymaster OAuth token, 2026-11-12): metadata OK for all test tracks; audio-key request **0/2** on a token-authenticated session **and 0/2 again on a stored-credentials session** (the server-returned reusable credentials librespot caches). Auth method is exonerated — the refusal is account-level.
- Upstream: this is exactly [librespot#1649](https://github.com/librespot-org/librespot/issues/1649) (pinned; 181-comment thread read in full) and [librespot#1735](https://github.com/librespot-org/librespot/issues/1735). Maintainer verdict (2026-11-07, issue locked): *"Playback is broken for all Spotify accounts created after a certain cutoff… No workaround is currently known, and there has been no viable fix identified."* Now also in the [librespot README warning](https://github.com/librespot-org/librespot/blob/dev/README.md). The official clients use Spotify's alternate DRM (PlayPlay), which is DMCA-protected and unavailable to librespot (go-librespot had to remove exactly such code).
- **Falsified client-side theories** (all tested upstream): keymaster vs other client IDs, declared client version, product/device type, OAuth scopes, DNS tricks, pacing/backoff, zeroconf (bypasses the *login5* lock only, not this), stored credentials. **2026-11-12 follow-up sweep**: audio keys requested for EVERY file format in the track metadata (AAC_24 + OGG_VORBIS_96/160/320 on two resolvable tracks) — **0/8 granted**, all refused with code 0x0001; the refusal is format-independent and total. librespot 0.8.0 (2025-11-10) remains the newest release; no fix exists upstream. The account also shows two extra degradation shapes: metadata unparseable for some tracks (`Invalid state …`), files stripped from metadata for others (e.g. "Never Gonna Give You Up") — consistent with a server-side shutdown of the legacy protocol surface for this account cohort.
- This machine's system clock is also unstable (multi-hour jumps observed) — a separate environmental quirk worth fixing (it corrupts token-cache expiry math and can break TLS), but NOT the cause: the audio-key refusal is a server response.

### What changed in the app

Since playback is unfixable for this account, the fix targets the user-facing failure mode (silent skip-flailing with no explanation):

- `src/player.rs`: post-login **probe** — fetches a well-known track's metadata and requests its audio key; an explicit `AudioKeyError::AesKey` refusal sets `WorkerState::playback_blocked` (generation-guarded so stale probes can't apply after logout). All other outcomes fail open. Play commands now **fail fast** with a clear message instead of loading tracks that can never start.
- `src/types.rs`: `PlayerSnapshot.playback_blocked` + shared `PLAYBACK_BLOCKED_MESSAGE`.
- `src/ui/mod.rs` + `src/ui/theme.rs`: persistent warning-colored banner in the status line while blocked.
- `examples/playback_probe.rs`: new live-API diagnostic (token vs stored-credentials audio-key comparison; re-runs the playback OAuth itself if the cached token is dead).

2. **Spotify Soloist** — Spotify's official headless Connect client (announced 2026-08-13); x86-64/arm64 only, builds expire every 90 days.
